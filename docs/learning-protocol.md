# 学习协议：谁能改什么、凭什么改

2026-10-04 Dai 定（decision-log 19:37、19:44）。这份协议是整套系统的一部分，所有角色都要遵守：对局 agent、学习者、开发会话、运维会话，不管用的是哪个引擎（Claude、Codex 或以后的其他引擎）。

## 1. 要回答的问题

这套 agent 架构能不能**靠自己的对局经验**变强。具体做法是：拿一个它从没打过的角色（静默猎手），从 A0 开始，赢一局升一级，看它最高能爬到哪一级。只有每一项打法上的提升都能追溯到对局证据，这个结论才站得住。

## 2. 两类改动

| | 游戏知识 | 系统 / 架构 |
|---|---|---|
| 是什么 | 机制怎么运作（毒、小刀、弃牌、Sly……）、牌和遗物的价值、怎么打某个怪、路线和构筑的取舍 | 模块怎么配合、数据怎么流、学习闭环怎么跑、角色和引擎的适配、日志、卡死、崩溃、接口错误 |
| 从哪里来 | **只能来自学习者对对局证据的分析** | Dai 和 codex 学习者 |
| 人能不能给 | **不能**。Dai 不提供；开发会话也不能把自己的游戏知识塞进去 | 能。Dai 参与架构调整 |
| 例子 | 「毒伤要算进斩杀」「这张牌值得拿」「这个精英要先打谁」 | 「学到的机制规则怎么让求解器读到」「复盘按角色分批」「换一个学习者引擎」 |

拿不准属于哪一类的，按游戏知识处理，或者问 Dai。

**通用能力可以由人来做，具体内容必须学出来。** 举个例子：「让学习者写的机制规则能进入求解器」是架构；「毒每回合扣多少、什么时候扣」是游戏知识。

## 3. 游戏知识怎么进入系统

```
对局日志 ──▶ 复盘（学习者） ──▶ 经验 / 知识数据 / 修复提案（学习者） ──▶ 自测（codex 学习者） ──▶ 自行上线 ──▶ 评估
```

1. **证据**：`logs/`（决策、状态、大脑问答、战斗）和 `notes/lessons.md` 里的复盘。
2. **学习者的产出**，每一条都必须带证据局号：
   - 经验条目：写进 `knowledge/characters/<角色>/experience.json`，要有证据局和置信度；
   - 知识数据：写进 `knowledge/characters/<角色>/` 下的选牌、提示、SL 名单等；
   - 修复提案：写清楚现象、证据局和回合、推断的原因、建议的改法。哪些需要改代码（比如求解器漏算某个机制），哪些只改数据就够，都在提案里说明。
   - 涉及出牌、药水、SL、终局价值的经验，除经验库外**必须同时有代码提案**；提案写适用角色/已观察进阶、证据/反例、账本 id、旧/新行为、验证及回退，关联来源学习任务和实现任务。用 [代码提案闭环](learning-code-proposals.md) 的 CLI 登记，调度器保存未完成项并自动派独立策略学习任务；证据不足留档等新局再审，不静默丢掉。
3. **Codex 学习者闭环**（Dai 2026-10-05 00:19、00:2x）：学习者核对证据、实现、用沙箱入口自测，通过就按 live 流程自行合入，不另设审核。实现只依据本角色对局证据，不添加证据以外的游戏知识。证据不足就记录未修，不凭自己的游戏知识补齐。运维 codex 根据完成事件确认实际合入、登记上线；学习者提交或合入受阻时兜底。Claude 只观察和与 Dai 对话，不修改或审核。
4. **记录**：每次上线在 decision-log 里写一行，包括来源（提案文件或复盘段落）和**来源局号**；改变对局行为时在 `eval/versions.json` 加一个版本，纯派发/模板记录不造版本。论文靠这些区分「学出来的」和「人给的」。学习者的每个发现和它之后的去向（提案、审核、上线的版本、上线后的效果）同时记在学习账本 `paper/materials/learning/ledger.jsonl`（只经 `learner/ledger.py` 追加；运维 codex 在核实实际合入后登记 `shipped`，保留历史审核记录，不另设审核）。

Roy 2026-10-07 12:22、12:35 新授权优先于旧模板限制：学习者有足够理由和自己核实的本角色数据时，可直接改 Roy 定的规则（包括药水持有价值、必死/SL、终局价值），固定自测通过就上线，不再因“人定”本身要求审批。授权不是游戏知识，具体条件/参数仍必须从对局学出；没有证据不改，无关角色/未观察机制保持等价。实际上线后先 `date`，项目根目录 `notes/for-dai.md` 与 `ops/inbox-dev.md` 双通知 Roy，逐项写旧规则、新规则、证据局/账本、预期影响和回退方法，并 CLI 登记台账。这是本流程明确授权的追加记录例外，不覆盖并行记录、不改运维 prompt。尚未授权的架构调整仍按原边界处理。

复盘必须追溯关键进场HP/药水被前面哪些战斗消耗，包含赢的战斗；SL恢复、回血、弃药与实际喝药分开，缺帧/缺反事实写未知，不以另一选择“本可赢”替代证据。

## 4. Codex 学习者可直接修的

- 和角色无关的缺陷：卡死、崩溃、接口和协议错误、日志、统计口径、构建器。
- Dai 批准的架构调整。
- 让系统能正确运行一个新角色或新引擎所需的适配。前提是不带入游戏知识：新角色的知识从空开始，不读别的角色的数据。

这几类修复同样要记 decision-log。如果修复会改变对局行为，还要在 `eval/versions.json` 加一个版本。

沙箱内自测用 `agent/tools/test-sandbox.sh`；排除文件与限制原因固定在脚本里。经验和修复批次完成后发 `experience-done` / `fix-done`，实际合入 live 后调度器在沙箱外跑完整 tsc + vitest，结果发 `learner-checks`；失败写收件箱，由运维 codex 决定回滚还是派修复。

## 5. 按角色隔离

- 每个角色的打法知识和统计只放在 `knowledge/characters/<角色>/`，也只从这里读。读不到就当作还没有知识。
- `knowledge/common/` 只放和角色无关、从游戏观察得到的事实，例如怪物的出招。
- 复盘、经验批次、指标、停止脚本都按角色分开，不同角色的数据不能混在一起。

- 默认每个角色赢一局升一级（`TARGET_ASCENSION` 的自动升阶模式），从 A0 开始。
- SL 之后的胜利也算赢。统计时第一次尝试和 SL 之后的结果分开记。
- Roy 2026-10-07 授权后，默认爬塔战绩与自动升阶只纳入可追溯的纯 Codex 脑局；DeepSeek、混合和未知来源单列原始成绩。复盘证据、费用和全部原始日志保持，显式全引擎口径可重现旧统计。具体定义见 [Codex 大脑等待与战绩口径](codex-only-brain.md)。
- 每次实际记录的 climb 升阶自动保存独立学习者升阶结构审计请求；有新等级已结束的本角色局后，比较实际层数/战斗场数、回血/营火/新规则与代码假设，列差异和代码提案。调度器按角色/等级去重，保存失败重试及工作树租约，不阻塞对局，不从跳级缺失记录推断未观察等级。首次安装只补当前已观察等级；失败旧树/日志保留，租约未释放不重复派。运维只核实登记，不添加游戏知识。

## 7. 引擎无关

学习者、开发会话和运维会话都可以换引擎，所以协议不依赖任何一家的特性：

- 规矩写在仓库里：本文件、[AGENTS.md](../AGENTS.md)、`learner/tasks/*.md`。不放在某个引擎自己的记忆或配置里。
- 学习者通过统一的启动器 `learner/run.ts --engine <名字>` 运行，任务说明不写某个引擎特有的工具名或模型名。启动器负责把任务要求翻译成各引擎的权限，比如 claude 的 `--tools`、codex 的 `--sandbox`。
- 产出都是仓库里的文件和提交，格式固定：复盘段落、experience.json、提案 Markdown，加上任务末尾的 json 回报块。换了引擎，下游照样能读。
- 对局中的大脑引擎（codex）和学习者是两套进程。大脑的 codex 关掉了项目文档（`project_doc_max_bytes=0`，工作目录在 /tmp），不会读到本仓库的 AGENTS.md。

## 8. 混杂因素（写进论文）

大模型（GPT、DeepSeek）在预训练时见过一代《杀戮尖塔》的静默猎手，这部分知识无法屏蔽。能做到的只有两点：不在提示和知识库里额外提供；在分析时把「第一次就做对的」和「输过之后学会的」分开统计。
