# 下一版架构提案：在"DS 定方向 / Jev 出牌 / 代码管死操作"的基础上修正

**总体判断：** 你提出的三层分工方向是对的，但有四处需要修正。
1. **战斗的主人应该是 solver，而不是 Jev。** 开源项目里强的 bot 打战斗都靠搜索。destire-mio 试过 6 种用网络替代搜索的方法，全部失败。所以 Jev 的角色是"在 solver 认为差不多的几条线里挑一条"。
2. **构筑现在其实是代码在做。** reward/card 有 74% 由卡牌分数表加 margin 决定，DS 只占 20%。要让 DS 真正负责构筑，得先把决策权交出去，再给它一个模拟出来的依据，用来压低它的方差。
3. **DS 应该完全退出出牌。** 它有拿 HP 换伤害的老毛病（DS 1.7 HP 换 0.4 伤害），而且现在 combat plan+potion 里有 64% 由它决定。
4. **"跨局决策"不适合放在 DS 身上。** DS 每次调用只看得到本局的信息。跨局的经验应该由赛后复盘层负责，它离线写入经验库，DS 和 Jev 在局内读取。

## (1) 各类决策的分工
| 决策 | 负责方 | 说明 |
|---|---|---|
| 出牌 | solver 为主，Jev 选差不多的线 | solver 枚举、打分，差距小于 6 时问 Jev。Jev 置信度低时不再升级给 DS，改由 code rank1 加 HP guard 决定。 |
| 药水 | 代码 + Jev；精英/Boss 战开局由 DS 定策略 | 药水的效果建模和"满槽就喝"之类的规则属于代码。"这场是否该交药、在哪一回合爆发"由 DS 在精英/Boss 战开局时一次性给出 fight_plan。 |
| 选卡 | DS | 调低代码 margin，只要候选卡里有能改变构筑方向的，就交给 DS。附上模拟值：带上这张卡和不带它，各跑 N 次下一个精英/Boss 的战斗，比较 HP 损失。 |
| 商店 | DS 出购买意向，代码执行 | 代码负责钱是否够、删卡顺序、丢垃圾药水。买哪一件由 DS 结合当前构筑方向决定。 |
| 事件 | DS | 代码继续过滤会危及 HP 的选项（event HP guard）。 |
| 升级 / 删卡 | 代码 | 删卡顺序（诅咒 > Strike > Defend）是确定的。升级优先级改由当前构筑方向决定，只在关键卡（例如方向核心卡）上问 DS。 |
| 地图 / 休息 | 代码打分 + Jev 选差不多的 | 精英要不要打的阈值（0.8/0.7）由 DS 的方向文档调节，比如"本局缺输出，Act2 不主动打精英"。 |
| Boss 专属打法 | 经验卡 + DS fight_plan | 把 card-value 里 7 个 Boss 的加分从死规则改成经验卡，而且只在对应 Boss 时触发。 |
| 构筑方向 / 中途转向 | DS | 在 Neow、第 6 层前后、每个 Act Boss 之后、拿到关键遗物或卡时调用。它输出结构化的 run_direction：{流派, 缺什么[], 避开什么[], 什么情况下转向}。代码把这份文档转成选卡加分（need bonus），替代现在固定的 +12/+14。 |

## (2) 经验怎么流动，以及怎么避免变成死套路
复盘 subagent 把每条教训分成 4 类，每类有固定去处：
- **A. 机制、bug** → 代码。34/45 的输局属于这一类，修一次基本不再出现。
- **B. 安全底线** → guard。
- **C. 可以量化的取舍**，例如"成长型能力卡值多少、当前防御值多少" → 改 solver 的打分项，并用 replay 离线验证。这是 bottled_ai 的做法：用约 40 个加权打分项加搜索，而不是写"遇到 X 就做 Y"。
- **D. 依赖具体情况的经验** → 经验卡。每张卡包含：触发条件（敌人、Boss、遗物、界面、HP 区间）、不超过 25 字的正向条件句、来源局、支持和反对的次数。

经验卡怎么升降级：
- **升为代码**：至少 3 局的证据一致，并且 replay 证明它每次都成立。
- **降级或删除**：连续 N 次触发都没有带来好处，就过期。
- 卡牌分数表只作为给 DS 的先验分数。只剩 1 局证据的规则（Boss 加分、Breakthrough 62、Armaments 48、Dark Embrace 至少 3 张消耗卡、keep 4 attacks）先降级成经验卡。

**已知冲突要单独处理。** JEGBU7 这局，HP guard 和能力卡的价值互相拉扯。解法是给 solver 加一个"成长收益 × 本场剩余回合的估计"打分项，而不是继续调 guard 的阈值。

## (3) Jev 能否通过 prompt 拿到经验
能，但只能放在 state 或 question 里。它没有 system 字段，也不能微调。按效果从高到低有三种渠道：
1. **在每个选项上加标签。** 由代码算出事实，例如 `setup_turn`、`hp_after`、`lethal_next_turn`、`wastes_block`。Jev 只会照字面理解，所以判断应该让代码做完再告诉它。
2. **加一个 `fight_hints` 字段。** 按敌人、战斗类型、HP 区间检索，最多 5 条，约 200 tokens。
3. **在 combat state 里删掉整份卡组和遗物列表。** 按文档的说法这些是干扰项，只保留战斗中会生效的遗物。

不能把整本手册（约 8–9k tokens）塞给 Jev。成本和延迟几乎不变：输入从 1k 到 3k tokens 时 p50 都在 530ms 左右，每次调用约多花 $0.00001。风险在于它会照字面误用经验卡，所以每张卡都要写清条件。DS 可以接收更多触发的经验卡。

## (4) 延迟和成本
- 现在约 380 次决策/局，DS 约 30 次，约 6 分钟。
- 新方案：DS 退出出牌，每局省约 21 次调用、约 4 分钟。新增构筑方向约 4 次、选卡约 13 次、商店约 6 次、事件约 5 次、精英/Boss fight_plan 约 8 次，每局约 36 次、约 7–8 分钟，占 45–60 分钟一局的 15% 以内。
- 选卡模拟放在本地 solver 里跑，每次预算不超过 3 秒。
- Jev 的调用次数不变，成本可以忽略。

## (5) 迁移步骤（每步可单独回滚）
**M0：先跑完 10 局作为基线。** 记录：A2 胜局数、平均层数、精英/Boss 平均掉血、出牌比 min-loss 多掉的 HP（现在 Jev 2.59 / 加 guard 后 1.88）、各层决策占比、每局时长。

**M1：Jev 的选项标签 + fight_hints + 精简 state。**
- 先用 `src/replay/replay.ts` 重问已记录的差不多的出牌决策，做 A/B。
- 指标：多掉的 HP 从 2.59 降到 2.3 以下，升级给 DS 的比例变化不超过 5 个百分点。
- 离线达标后才上线。

**M2：出牌时 DS 退出。**
- Jev 置信度低时，由 code rank1 加 guard 决定。
- 指标：10 局中出牌多掉的 HP ≤ 1.88，每局少 3 分钟以上。

**M3：DS 在检查点输出 run_direction，代码据此调整选卡加分。**
- 指标：方向一致的比例（离线人工抽查），Act2 精英平均掉血下降，平均层数不低于基线。

**M4：选卡改由 DS 决定，附带模拟值。**
- 指标：DS 的选择与模拟值最优项的一致率，10 局平均层数和 Act2 通过率。

**M5：把 D 类中只有单局证据的规则迁移成经验卡。**
- 指标：10 局不退步（平均层数在基线 ±2 以内）。
- 这一步的目的是减少死套路，不是提高胜率。

**M6：精英/Boss 开局由 DS 输出 fight_plan，转成 solver 的打分调整和 Jev 的 hints。**
- 指标：Boss 战平均掉血，Act1/Act2 Boss 的胜率。

## (6) 主要风险
- **样本太小。** A2 的胜率接近 0，10 局看不出显著差异。应该主要看层数、每场掉血、replay 这些细粒度指标，胜率只作参考。
- **DS 构筑方差大。** 两次胜局靠它，失控的也是它。所以必须给它模拟值和方向文档做约束，并保留代码对明显坏选择的否决（比如卡组膨胀、没有 AOE）。
- **Jev 照字面误用经验卡**，比如在能斩杀的回合优先出能力卡。缓解方法是选项标签由代码计算，经验卡写清条件。
- **经验卡越积越多，又变回死套路。** 缓解方法是每张卡有过期机制，每次调用最多 5 条，统计每张卡被触发和被采纳的次数。
- **经验不能在模型之间直接迁移。** AgenticSTS 为 Gemini 写的 skills 放到 DeepSeek V4-Pro 上反而掉了 18%。所以 DS 的提示和经验卡都要在 DS 自己身上做 A/B。
- **每一步都要记录谁在决策，并能回滚。** 所有决策继续写入 `jev-sts2/logs/decisions.jsonl`，用 source 字段区分，方便复盘归因。
